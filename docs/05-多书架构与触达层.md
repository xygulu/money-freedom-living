## 0. 一句话

> **产品的主体是用户，不是书。**
> 用户的认知成长是**跨书累计的一段过程**；书是这段过程的**燃料与入口**；把两者接起来的是**命题**。

§7 已经写过这件事（*"每本书只是六个命题的一个切面；以命题为跨书索引，书只是燃料"*），**本文是把它落成数据模型与界面**。

## 1. 问题从哪来

用户原话（2026-09-14）：

> 「当前是基于《不愁钱》一本书，你需要考虑产品框架能够容纳不同书的内容，内容层是单独的，每个用户也可以有多本书，但是多本书对于同一个用户是融合的还是单独的我没想好，也就是说用户认知成长变化是基于用户的，还是基于书的，我倾向是基于用户。」

**定案：基于用户。**

## 2. 三层分离（架构主干）

## 3. 关键设计

### 3.1 ★ 书是「区域」，不是「进度条」

**这条决定换书会不会痛。**

| 建模 | 换书时用户感受到的 | 结果 |
|---|---|---|
| 书＝进度条 | "我的进度清零了" | ❌ 觉得白做了 |
| **书＝区域** | "地图变大了，原来那件事还有另一个说法" | ✅ 是**扩展** |

界面落点：路标是**区域**，不是"第几本书的第几章"。

### 3.2 ★ 灯必须从「书的阶段」里拆出来（多书能 work 的关键）

现状：灯挂在书的阶段上（阶段 1/2/3 各 3/3/2 盏，而阶段定义来自《不愁钱》）。拆成两样：

- **书的阶段** = 该书的**路线图**（可换、可弃）
- **用户的灯** = 他在**某个命题上的程度**（**不可重置、永久累加**）

**新书进来只增加新灯位**，已有的灯**不动、不灭、不重置** —— 这是既有「灯不熄灭、阶段不倒退」原则的自然延伸。

**实现靠改常量、不改表**（见 §4.6）。

### 3.3 同命题撞车是特征，不是 bug

两本书都说"我不配"，用户会嫌重复。必须处理成**"不是重复讲，是从另一个角度切同一件事"**，并**把他上次的原话调出来**：

> 「三个月前你说过'我不配闲着'。这本书说的是同一件事的另一面。」

**这才是多本书真正的价值：交叉印证**（11 个机制里本来就有这一条，属「换掉」阶）。

⚠️ 反指标：处理成"又一次讲我不配"，用户会觉得产品在糊弄。

### 3.4 接第二本：不看进度，看信号

不是"读完第一本"，是"**第一条命题线上出现「用熟」迹象时**"才接。数据触发，不是进度触发。

### 3.5 书的身份：可见但弱化 `[用户已拍板]`

- 书**只出现在「你走过的路」里** —— 作为**出处**（这段路来自哪本书）与**邀请**（"这本书说完了，还有一本书从另一个角度说同一件事"）
- 书**不出现在日常页、不出现在进度/灯/计数里**
- **用户的心智锚点是命题，书是他能选的入口**（不是"我的书架"，是"我这件事，还有谁说过"）

## 4. 数据模型改动（M11-A）

### 4.0 结论先行：**零新表**（但有一张既有表要加 1 列）

**不新建任何表** —— 用户数据全部用 `growth_profiles` 行内 JSONB 承载。

⚠️ **精确表述：「零新表」≠「零改动既有表」。**
`consent_records` 要加 1 列 `kind`（**唯一一处改动既有表**，见 §4.8）。

不建新表也不是图省事 —— docs/03 §3 自己写明了这是**故意**的设计：

> 「在行内 → **导出/删除/游客迁移天然覆盖**」

**新建表的隐性代价（仓库里真实存在、必须手工补的三处）：**

| 位置 | 漏掉的后果 |
|---|---|
| `src/lib/migrate.ts` 游客→账号迁移白名单（现 7 张表） | 游客期数据**登录后丢失** |
| `src/app/api/me/export/route.ts` | 用户导出档案**缺这一块**（合规） |
| `src/app/api/me/delete/route.ts` | 删除账号**删不干净**（合规） |

### 4.1 `growth_profiles` 加 3 列（幂等 `ADD COLUMN IF NOT EXISTS`）

| 新列 | 类型 | 内容 |
|---|---|---|
| `books` | `JSONB DEFAULT '[]'` | 书位：`[{bookId, status:'active'\|'paused'\|'done', startedAt, stage, stageStartedAt, finishedAt?}]`。**当前书 = `status='active'`**，不另加 `active_book` 列（避免两处真相） |
| `threads` | `JSONB DEFAULT '{}'` | **命题线**：`{ [topicId]: { firstSeenAt, lastSeenAt, depth:'seen'\|'replaced'\|'mastered', evidence:[{at, bookId, source, quote, ref}] } }`。`source` = `chat\|journal\|letter\|experiment\|assessment`；`quote` 必须是**用户原话** |
| `touch` | `JSONB DEFAULT '{}'` | 触达状态：`{ emailOptIn, optInAt, unsubToken, lastSentAt, sentNodes:{D7:at,…}, lastOpenedAt? }` |

**存量数据归位**：存量用户在 `books` 读时补一条 `{bookId:'money-freedom', status:'active'}`（`DEFAULT_BOOK_ID`，**不写迁移脚本**）；其余数组**缺 bookId 的条目一律视为该书**。
段数以行级 `stage` / `stage_started_at` 为唯一真源（`books[]` 里 active 那条读时被覆盖，避免两处真值）。

### 4.2 已有 JSONB 数组加 `bookId?`（向后兼容，无需迁移）

| 字段 | 用途 |
|---|---|
| `memories[]` | 交叉印证时知道"这句是读哪本书时说的" |
| `experiments[]` | 按书统计动作完成 |
| `letters[]` | 「你走过的路」标出处 |
| `stamps[]` | 心印陈列按区域分组 |
| `dailySeen[]` | 池按书选；**去重仍按用户全局**（同一张签不给两次） |
| `concerns[]` | 困扰的来源书 |

⚠️ `portrait` / `portrait_evolution` **不动** —— 画像**归用户**，跨书演进，版本号是用户级的。

### 4.3 `portrait_versions` 加 1 列

| 新列 | 说明 |
|---|---|
| `bookId TEXT NULL` | 记录**触发这一版演进的书**。**`UNIQUE (user_key, version)` 不变**（版本序列是用户级的） |

`source` 枚举加值：`onboarding \| evolve \| backfill \| book_switch`。

### 4.4 明确不动的表（防误改）

`chat_sessions` · `chat_messages` · `journal_entries` · `safety_events` · `events` · `recovery_attempts` · saas-kit 的 `subscriptions` / `entitlements` / `quota_events`

（`consent_records` **不在此列** —— 它要加 1 列，见 §4.8）

**理由**：都是**行为流水**，天然属于用户而非书；加 bookId 只会让表变脏，需要时按时间关联 `books[].startedAt` 推导即可。

### 4.5 6 个阶段验证节点：**零 DDL**

- **第 N 天不存** = `now - growth_profiles.created_at` 纯函数推导（与既有「读时纯函数推导，自愈」纪律一致）
- **结论落 `events`（已有表）**：`name='node_verdict'`，`metadata={node:'D14', verdict:'成立'|'不成立'|'待续', metric, value}`
- 提前收官 / 三态判断 / 收敛速度 = `events` 读时聚合

### 4.6 灯的存法：**改常量，不改表**

- `stage_assessment.confirmed.lamps[].kind` **保持原样**（它描述的是这本书的一次评估）
- 改动在 `src/lib/stage.ts`：`STAGE_LAMPS` 索引从 `stage:number` 改为 `bookId + stage`，每条 `LampRule` 新增 `topic: TopicId`
- **两种读法（分层，不冲突）**：书内进度 = `confirmed.lamps`（不变）；**命题程度（跨书累计）= `threads[topic].depth`**（新）
- 评估确认时**多一个副作用**：把本次点亮的灯按 `topic` 派生写入 `threads[].evidence`（`source:'assessment'`）

> 旧书的灯 `kind` 不变 → `confirmed.lamps` 历史**一个字不动**。

### 4.7 优化留痕**不进库**

它是**产品变更日志**，该跟代码走版本控制：仓库内 `optimizations.json`（读时作为 `contentVersion` 注入）。进库反而要新建表，破坏"零新表"。

### 4.8 `consent_records` 加 1 列 `kind`（**唯一一处改动既有表**）— ✅ 已实现（`87d53da`）

**实读结论**（`src/lib/consent.ts` + `src/lib/db.ts` 建表语句）：

```sql
consent_records (id, user_key, granted BOOLEAN, policy_version, ip_hash, created_at)
```

**没有类型字段。** 这张表是**专门为「敏感信息单独同意」建的**（文件 docstring：「敏感信息单独同意（docs/02 §9：金钱困扰、童年记忆、心理状态可能构成敏感个人信息…）」）。

→ **必须加列**，否则「同意生成画像」与「同意收邮件」会混成一条。

| 新列 | 类型 | 说明 |
|---|---|---|
| `kind` | `TEXT NOT NULL DEFAULT 'sensitive'` | 取值：`'sensitive'`（画像与深谈；**存量记录全部归此类**）｜`'touch'`（触达 opt-in） |

**实际实现**（`src/lib/db.ts`，照此对齐）：

```sql
ALTER TABLE consent_records ADD COLUMN IF NOT EXISTS kind TEXT NOT NULL DEFAULT 'sensitive';
CREATE INDEX IF NOT EXISTS idx_consent_user_kind ON consent_records(user_key, kind, created_at DESC);
```

> 旧索引 `idx_consent_user (user_key, created_at DESC)` **保留未删**（新索引已覆盖其用途，旧索引冗余但无害；要清可在后续迁移里单独 `DROP INDEX`）。

> **默认值方向必须搞对**：`DEFAULT 'sensitive'` 是**保守**方向 ——
> 万一将来某处「触达同意」的写入忘了传 `kind`，结果是**被记成画像同意**（＝改动前的旧行为），
> 而**不会**被误记成"已同意收邮件"（那会直接导致违规发信）。
> 默认成 `'touch'` 是**危险方向，不能这么设**。

#### ⚠️ 加列会牵出一个必须先修的静默坑

`src/lib/consent.ts` 的 `latestConsent(userKey)` 现在是：

```sql
SELECT granted, ip_hash, policy_version, created_at
FROM consent_records WHERE user_key = $1
ORDER BY created_at DESC, id DESC LIMIT 1
```

**没有按 `kind` 过滤。** 加了 `kind` 之后它会**跨类型取最近一条**：
用户刚点了"同意收邮件" → 画像入口读到的就是**触达同意**那条，**误判成敏感信息已同意**（反之亦然）。

**必须同步改** `latestConsent(userKey, kind)`（WHERE 加 `AND kind = ${kind}`），并检查所有调用点都传对 kind。

> **这是本次改动里最容易漏、后果最直接的一处** —— **它不会报错，只会静默给出错误的同意状态。**

## 7. 上手路径（M11-C）：3 分钟拿到第一个"我的东西"

**现状**：问卷 6 题 → AI 初谈 3-5 轮 → 「我听到的是…」→ 生成画像 → 校准（目标 10 分钟）。
**问题**：要 5 步才见到第一个成果，太重。

**改法**：把「我听到的是…」**前置到第 2 分钟**——这一句就是**第一个物件、第一次被说中**；完整画像随后。

**顺序铁律**：**先被说中 → 再注册 / 同意 / 定价**。
⚠️ 敏感信息单独同意弹窗（P§9）**绝不能插在"被说中"之前** —— 现在的实现是插在画像生成前，要往前挪一个位置，挪到"被说中"之后、画像生成之前。

**指标**：首次"说中了"耗时 **< 3 分钟**（进埋点）。

## 8. 日频形态（M11-D）：从「三件事」到「一段」

**现状**：`/journey` 三张卡片（今日一签 / 今日微行动 / 陪伴对话）。
**问题**：三张卡片＝三个未完成项＝**天然欠账感**。

**改成有形状的一段：**

```
开（看见）  →  做（动手）      →  合（被看见）
今日一签        一个 2 分钟动作      一句话被接住 + 明确收束
```

**硬规则**
- **只看那一眼也算走完这一段**
- 结尾是「**今天到这里**」，不是「明天还有」
- 既有的「全部可跳过、跳过不断足迹、无红点」**保留**

### 8.1 设计依据：这是「世界感」，不是「游戏化」

参考游戏是《纪念碑谷》《地狱边境》——**这两款一个成就系统都没有**：没分数、没等级、没奖励、没排行榜。
⚠️ **易被误读成"要加积分"，那会推翻已否决的「游戏化等级/连续打卡」决定。方向恰恰相反。**

| 游戏里的做法 | 产品对应 |
|---|---|
| 回去不是因为被叫，是**看见了远处还没走到的那座塔** | 召回＝**可见的未完成风景**。「展示未来 ≠ 展示欠账」 |
| 零台词零教程，叙事由**画面与物件**承载，解读权全给玩家 | 关键节点**不给结论，给物件**；物件上只放他自己的原话，**不写"你进步了"** |
| 每章 8–15 分钟**自包含**，有始有终，然后可以合上，不欠债 | 每天回来是**一段完整体验**，不是待办清单 |
| 零失败态、试错代价极低 | 跳过不断足迹、只增不减、可回退（现状已对，再彻底一点） |

### 8.2 目标口径的修正 `[待你确认]`

**不要把"用户愿意每天主动使用"直接当目标。**
心理类产品（金钱焦虑尤其）硬拼日活会**反过来伤用户**。改为：

1. **每次回来都有确定的质量**（一小段完整体验）
2. **想面对钱的那一刻，第一个想到的是它**

→ 日频不靠意志力，靠**跟真实情绪日历走**（发薪日/月底/还贷/大促）。现状的「周期情绪锚点」**是对的，保留并加强**。

## 9. 邮件触达层（M11-E）

### 9.1 通道（用户已定）

| 阶段 | 产品载体 | 主动触达通道 |
|---|---|---|
| **一期** | **H5** | **邮件** |
| 二期 | iOS App | **iOS 通知（APNs）** |

人群因此走**海外路线**（Creem + 四语保留，不面向中国大陆境内）。

### 9.2 邮件不是"推送的劣化版"，它恰好是产品的原生形态

**产品的原生仪式本来就是"信"**（「给钱的一封信」「给未来自己的信」）。所以召回**不写推送文案，写成信**：

> 「三个月前，你写过一封信。它还在。」

**基础设施已存在**：`src/lib/email-resend.ts`（现用于恢复码/删除确认），**直接复用，不新建通道**。

### 9.3 三条硬约束

1. **邮件是"节点召回"，不是日活引擎。** 适合 D3/D7/D14/21/30/66/90 与"悬着的东西"，**不能天天发** → **日频只能靠 §8 的产品内机制**。
2. **营销邮件需 opt-in + 退订**（GDPR/CAN-SPAM），**触达同意必须与「敏感信息同意」分开**，不打包勾选（P§9 新增一条）。
   → **落地就是 §4.8**：`consent_records.kind = 'touch'`，与 `'sensitive'` **分开存、分开读**。
3. **送达率是工程量**：发信域名 SPF/DKIM/DMARC + 预热。**不做这项等于没有触达**（信进垃圾箱）。

### 9.4 触达语义（红线拆分）

现状红线写的是「产品永不主动追问、无打卡、无断签召回」。**拆成两半：**

- ✅ **保留**：不催促、不断签、不欠账、不评判
- ❌ **废掉**：「**不主动出现**」—— 那只是实现手段

> **理由**：把主动触达整个排除，等于**产品没有任何能力把人叫回来** ——
> **"不打扰"的等价物是"这个产品不存在"。**

**唯一允许的句式：**

| ❌ 禁止 | ✅ 允许 |
|---|---|
| 你还没做 / 你已经 3 天没来 / 别忘了今天的练习 | 它记得你说过 X / 上次那封信它回好了 / 今天是发薪日 |

### 9.5 新增组件（本次唯一全新系统能力）

| # | 内容 |
|---|---|
| 1 | **调度**：现状**没有任何定时能力**（只有 `scripts/*.mjs` 手动脚本）。需定时扫 `growth_profiles` → 算"谁到了 D7/D14/…" → 发信。自托管环境先用 `systemd timer`（零新依赖） |
| 2 | **触达模板**：按"信"的形态写；首条建议 `D3 未归` →「你上次说到 X，它还在」 |
| 3 | **opt-in + 退订**：onboarding 里**单独一项**触达同意；`touch.unsubToken` + 退订路由；每封带退订链接 |
| 4 | **重发防护**：靠 `touch.sentNodes`（每节点只发一次），**不要靠"脚本不重复跑"** |

### 9.6 落地后的七条工程口径（docs/07 P1 批次，实现即定案）

| # | 口径 | 为什么是这个数/这个做法 |
|---|---|---|
| 1 | **最小间隔 `MIN_GAP_DAYS = 4`** | 被节点表逼出来的：D3 → D7 只差 4 天，门槛定 5 就会把 D7 推到第 8 天之后。D7 是留存的关键断点，晚一天就是晚一天 |
| 2 | **「人还在不在」按节点定门槛**：D3 要求离开 ≥1 天，其余 ≥2 天 | D3 冲的是"第三天断崖"。要求连着两天不来，等于 D2 露一面就把这次干预推迟——那就错过了它唯一想接住的人。判断挪到选完节点之后（先知道是哪一封，才知道用几天的门槛） |
| 3 | **引用的那句话按时间取最近**（信与命题线原话一起排序） | 记得住的体感来自**近**，不来自**多**。否则 D90 还在引用第 5 天写的信，"我记得你"就成了"我停在你三个月前" |
| 4 | **退订两步**：`GET` 只送到确认页（零副作用），`POST` 才真退 | 邮件客户端/企业邮关会**预取**信里每条链接做安全扫描 —— 老的 GET 即退会让人在毫不知情时被退订。GET 不该有副作用是老规矩，之前那版赌的是用户的知情权 |
| 5 | **RFC 8058 一键退订**：信头挂 `List-Unsubscribe` + `List-Unsubscribe-Post` | 真正要"一下就成"的场景由收件方（Gmail/Yahoo 2024 起对批量发信的要求）提供，它替用户 POST 过来 —— 一键和确认页两条路同时成立 |
| 6 | **占位回滚分两类**：401/403/422 → 还回占位并**中止整轮**；超时/5xx → 保留占位 | 前者信确定一个字没出去，且下一个人一定一样失败；后者送没送到不好说，撤回就有重发的风险。宁可漏发不可重发，但不能漏得无声无息 |
| 7 | **归因**：信里的回程链接带 `?from=touch&node=D7`，journey 页据此记 `touch_return` | 寄出去和有人因此回来是两回事，只有后者能回答"这些信该不该继续写"。页面上一个字都不显示 |

**产品侧仍悬着**（不是代码问题，需用户拍板/操作）：`_dmarc.miller.ink` TXT 未加；发信域名仍借用 honghong 的 `miller.ink`，本产品该有自己的。

### 9.7 段数与灯：全部改为跟着当前在读的书走（docs/07 P2 批次）

M11-A 把灯表做成了按书索引（`BOOK_LAMPS` / `lampsFor(bookId, stage)`），但四个调用点还停在
第一本书上：`computeStageProgress` / `stageLampScales` / `stageAdvanceTarget` / `actionEvidenceKinds`
内部直接索引 `STAGE_LAMPS`，`stageLampScales` 的段数写死 `[1,2,3,4]`、`stageAdvanceTarget`
的上界写死 `MAX_STAGE`。接第二本书那天，这两处会一起说谎——段数不对、灯是上一本的。

| 口径 | 做法 |
|---|---|
| **段数属于书** | 新增 `stageCountFor(bookId)`（`content.ts`，叶子模块），从内容层的段自己数，不另立常量。认不出的书返回 0，由调用方决定回落 |
| **`MAX_STAGE` 保留但封存** | 存量引用还在，注释写明「新代码别再直接用它」。回落时写成 `stageCountFor(bookId) || MAX_STAGE`，保证进度栏不会是空的 |
| **`bookId` 是可选参数，默认 `DEFAULT_BOOK_ID`** | 存量调用点零行为变化（单测逐条比对「不传 = 传 v1」）。**不在 `stage.ts` 里直接调 `activeBookId`**——`profile.ts` 已 import `stage.ts`，反向引用会成环 |
| **由调用点传书** | journey 页传页内已有的 `bookId`；`JourneyProgressBar` / `profile.ts` 传 `activeBookId(profile)`；`assess.ts` 传 `context.bookId ?? DEFAULT_BOOK_ID`（同函数内本来就是这个口径） |

## 10. 验收

### A. 回归（必须全绿，一个不能少）
```
tsc --noEmit                        0 错
vitest                              (现 271) 全绿
scripts/smoke-m3 … smoke-m10        全通过
scripts/m8-safety-audit.mjs         16/16
scripts/repro-stream-mutex.mjs      9/9
scripts/repro-ux.mjs                playwright 全通过
```

### B. **存量用户零变化（本清单最重要的一条）**
> 一个存量单书用户升级后：**画像 / 灯 / 足迹 / 信 / 心印 / 每日一签去重**与升级前**逐项一致**。
> 做法：升级前后各导出一次档案 → **diff 必须只多出 `books`/`threads`/`touch` 三个键，别处零差异**。

### C. 多书隔离与合并
1. 给测试账号加第二本书 → 旧书的灯 `kind` **不出现在**新书评估里，且**不熄灭**
2. 第二本书某命题与第一本重叠 → `prompt.ts` 组装出的上下文里**出现第一本的用户原话**（交叉印证生效）
3. 同一用户两本书的 `dailySeen` 去重**仍全局生效**

### D. 合规
1. 未 opt-in 用户**收不到任何触达邮件**
2. 退订：`GET` 只到确认页且**不改任何字段**；`POST`（确认页表单 / RFC 8058 一键）才真退，且 `events` 有记录
3. 新建账号导出含 `books`/`threads`/`touch`；删除账号后**全部级联清空**（含新三列）
4. 游客期产生的 `books`/`threads`/`touch` 登录后**跟着账号走**
5. **两种同意互不串台**（§4.8 那个静默坑的守卫）：只同意画像、未 opt-in 触达的账号 → 画像入口判"已同意"、触达判"未同意"；只 opt-in 触达的账号 → 反之。**这条必须写成单测。**
6. 存量账号升级后，其历史同意记录 `kind` 全部回填 `'sensitive'`，且画像入口判定**与升级前一致**
